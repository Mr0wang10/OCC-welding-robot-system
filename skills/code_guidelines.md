# Code Guidelines

本规范用于指导 Agent 在 OCC_MFC 项目中的代码分析、设计与修改行为。

目标：

- 降低误修改风险
- 降低过度设计风险
- 保持项目风格一致
- 提高代码可维护性
- 保证修改可验证

## 1. Think Before Coding

先分析，再编码。禁止直接开始修改代码。

在实施任何修改前：

1. 明确理解需求
2. 分析影响范围
3. 识别相关模块
4. 检查是否存在歧义
5. 显式说明假设

如果存在不确定信息：必须说明假设。

例如：

> 假设当前STEP模型均为标准CAD模型。
> 假设机器人姿态单位为毫米和角度。

禁止在存在歧义时自行选择一种解释并直接实现。

### 不确定时主动询问

如果出现以下情况：

- 需求存在多种理解方式
- 修改可能影响现有功能
- 项目行为无法从代码推断

应停止修改并提出问题。不要猜测。

### 提供更简单方案

如果存在明显更简单的实现：应主动说明。

例如：

> 当前需求可通过修改现有模块实现，无需新增类或新增架构。

## 2. Simplicity First

优先选择最简单方案。只实现当前需求。

禁止：

- 提前设计未来功能
- 增加未被要求的扩展能力
- 增加未被要求的配置项
- 增加未被要求的抽象层

### 避免过度设计

禁止：

- 一个地方使用的代码 → 抽象出复杂框架
- 一次使用的逻辑 → 创建通用系统

除非用户明确要求。

### 保持代码简洁

在提交方案前自检：

1. 是否能用更少代码实现？
2. 是否增加了不必要的复杂度？
3. 是否符合现有项目规模？

如果答案是可以更简单，则优先简化。

## 3. Surgical Changes

最小化修改范围。只修改与当前任务直接相关的代码。

禁止：

- 顺手重构
- 顺手优化
- 顺手修改命名
- 顺手调整格式

除非任务明确要求。

### 保持现有风格

遵循项目已有：

- 命名方式
- 缩进方式
- 文件组织方式
- MFC消息映射风格
- OCCT代码风格

不要引入新的代码风格。

### 不主动删除旧代码

发现以下情况时：

- 未使用函数
- 未使用变量
- 历史代码

应报告，不要主动删除。除非用户明确要求。

### 仅清理自己产生的问题

允许删除：

- 本次新增但已废弃的代码
- 本次修改后产生的无用变量
- 本次修改后产生的无用头文件

禁止清理历史遗留问题。

## 4. Goal-Driven Execution

将需求转化为可验证目标。不要以"修改一下"、"优化一下"、"修复一下"作为结束标准。必须定义验证方式。

### Bug 修复

- 目标：能够稳定复现问题
- 验证：问题修复后无法再次复现

### 功能开发

- 目标：功能可执行
- 验证：结果符合预期

### 重构

- 目标：行为保持一致
- 验证：功能保持一致

### 修改前说明计划

对于复杂任务，先给出计划。格式：

1. 分析模块
   - 验证：确认影响范围
2. 修改实现
   - 验证：编译通过
3. 功能验证
   - 验证：结果符合预期

### 修改后验证

修改完成后必须说明：

- 修改内容
- 影响范围
- 验证方式
- 验证结果

## 5. OCC_MFC 项目专项要求

适用于本项目。

### 运动学相关代码

涉及 TCP、手眼标定、坐标变换、姿态计算时，必须确认：

- 单位
- 坐标系
- 欧拉角顺序
- 矩阵方向

禁止凭经验修改矩阵运算。

### OCCT相关代码

涉及 TopoDS、AIS、V3d_View、STEP 时，优先复用现有实现。禁止重复实现已有功能。

### UI相关代码

涉及编辑框联动、参数回填时，必须检查 `m_bIsUpdating`，避免递归触发事件。

## 核心原则

如果存在多个方案，优先选择：

- 修改最少
- 风险最低
- 最容易验证
- 最符合现有项目结构

而不是：最复杂、最通用、最"高级"的方案。
